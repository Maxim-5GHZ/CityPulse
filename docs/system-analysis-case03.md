# Системный анализ — Кейс 03 «Обнинск 2040: конструктор города будущего»

> Статус: утверждено. Роут — `/workspace/constructor` (внутри workspace, пункт `NAV_ITEMS`).
> Стек не ломаем: Next.js 14 + Spring Boot 3 (Java 21) + Postgres 16 + JWT, фронт в API только через same-origin `/backend/*`.
> Карта — **OpenLayers** (требование заказчика). 3D — Three.js. Ветер/тени — эвристики, не CFD. Данные эко — моки + адаптеры.

## 1. Паспорт кейса (что сказано в задании)

**Источник:** «ОБНИНСКИЙ ХАКАТОН 2026 / 16–17 ОКТЯБРЯ / ГОРОДСКАЯ СРЕДА / КЕЙС 03» (2 скрина).

**Суть:** интерактивный конструктор небольшого виртуального городского района. Пользователь меняет расположение объектов и сразу получает пересчет минимум двух показателей качества среды. Расчеты опираются на явные правила, а не на заготовленные ответы.

**Для кого:** горожане, архитекторы, урбанисты, проектные команды, городские организации.

**Почему важно:** при благоустройстве выбирают между парковками, озеленением, пешеходными связями, остановками. На словах преимущества каждого варианта звучат убедительно, но последствия для жителей непросто сравнить. Упрощенная модель района помогает увидеть, как изменение инфраструктуры сказывается на пешеходной доступности.

### 1.1. Обязательный MVP за два дня (п.4 — дословно)

1. Редактируемая схема района минимум с **10 узлами пешеходной сети, 5 жилыми объектами и 2 объектами притяжения**.
2. Не менее **двух действий** с инфраструктурой: добавить/убрать переход, изменить остановку, добавить зеленую территорию или перекрыть путь.
3. Пересчет как минимум **двух измеримых метрик**, например средней длины пути до остановки и доли условных жителей с доступом к парку в радиусе N метров.
4. Наглядное сравнение исходного и измененного сценария, включая объяснение алгоритма и допущений.

### 1.2. Что НЕ требуется (п.7 — дословно)

- Создавать точный цифровой двойник всего Обнинска.
- Подключаться к государственным геоинформационным системам.
- Рассчитывать транспортную модель города с реальными пробками.
- Подтверждать градостроительную законность предложенных решений.

### 1.3. Демонстрация и приемка (п.8–п.9)

- Жюри выбирает действие: например, закрыть один переход и перенести остановку. Команда меняет схему, запускает расчет и демонстрирует новую длину маршрутов и доступность объектов.
- При возвращении исходных параметров метрики должны воспроизводиться.
- Проверяются: настоящий пересчет после изменений, прозрачность показателей, удобство сравнения сценариев. **Декоративная карта без расчетной логики не считается полноценным решением.**
- Возможный техподход (п.10): графовые модели пешеходной сети и кратчайшие пути (Dijkstra/A*), React/Vue, Leaflet или простая SVG/Canvas-схема. Географическая точность реальной карты не обязательна.

### 1.4. Ограничение ответственности (п.11 — дословно)

Все население, маршруты и показатели в MVP условные. Полученные результаты нельзя представлять как официальный прогноз для городского планирования. В UI обязателен бейдж «данные условные».

### 1.5. Хотелки команды поверх кейса (зафиксировано)

1. 3D города (условный район Обнинска), видно как тень падает на другие здания.
2. Расчет ветра (эвристика).
3. Расчет теней (эвристика + 3D).
4. В 3D построить здание (коробку) и рассчитать как оно мешает потоку (пешеходному + ветровому).
5. API к загрязненности районов со спутника — карта загрязнений.
6. Карта грунтовых вод.
7. Небольшое заключение через эвристику (if-then, без LLM на демо).
8. Сохранение проектов (сценариев).
9. Карта — OpenLayers.

## 3. Глоссарий (единый язык)

- **Район** — условный квартал 1000×1000 м. Центр привязан к Обнинску только для солнца/розы ветров, геоточность не требуется (п.10).
- **Узел** — точка пешеходной сети `{id, x, y}` в метрах локальной сетки.
- **Ребро** — связь `{a, b, length, type, closed?}`, `type: тротуар | переход`.
- **Дом** — `{nodeId, residents}` — условное число жителей.
- **Притяжение** — `{nodeId, kind: остановка | парк | школа}`.
- **Здание-коробка** — `{footprint, h}` — экструзия для 3D/ветра/тени; влияет на граф (обход).
- **Сценарий / проект** — сохраненный `DistrictModel + seed + hash`.
- **Метрика** — число, которое пересчитывается Dijkstra заново после каждого действия.
- **До/после** — `baseline` (сид) vs `current` (после действий) + дельта.

## 4. Доменная модель — единый источник для 2D/3D/расчетов

Один TS-интерфейс, из него рисуются и OpenLayers-карта, и Three-сцена, и все расчеты:

```ts
// frontend/lib/city/model.ts
export interface CNode { id: string; x: number; y: number } // метры, 0..1000
export interface CEdge {
  id: string; a: string; b: string;
  length: number; // метры, считает turf или евклид
  type: 'trotuar' | 'perehod';
  closed?: boolean;
}
export interface House { id: string; nodeId: string; residents: number; label: string }
export interface Attraction {
  id: string; nodeId: string;
  kind: 'ostanovka' | 'park' | 'shkola';
  label: string;
}
export interface Building {
  id: string;
  footprint: [number, number][]; // полигон в метрах сетки
  h: number; // высота, м (3..75)
  label: string;
}
export interface Green { id: string; polygon: [number, number][]; porosity: number } // 0..1
export interface DistrictModel {
  seed: number;
  nodes: CNode[];
  edges: CEdge[];
  houses: House[];
  attractions: Attraction[];
  buildings: Building[];
  greens: Green[];
}
export interface Scenario {
  id: string; name: string; owner: string;
  model: DistrictModel;
  hash: string; // sha1 канонического JSON графа — для воспроизводимости
  createdAt: string; updatedAt: string;
}
```

**Сид P0:** 12 узлов, 5 домов (по 80–240 жителей), 2 притяжения (остановка + парк) + 1 школа опционально. Все координаты фиксированы через `seed`, чтобы «возврат = те же цифры».

**Проекция:** локальная сетка 0..1000 м маппится в `EPSG:3857` через сдвиг от центра Обнинска (55.0960, 36.6100). Подложка OSM приглушенная, поверх — `VectorLayer`. Геоточность не нужна, это выполняет п.7 и п.10.

## 9. Алгоритмы (душная часть)

### 9.1. Граф и Dijkstra — «настоящий пересчет»

Вес ребра = `length` (метры). Закрытое ребро исключается. Кратчайший путь — классический Dijkstra с бинарной кучей (граф ≤100 узлов, можно и O(V²)):

```ts
// frontend/lib/city/graph.ts — 30 строк, прозрачно для жюри
export function dijkstra(adj: Map<string, {to: string; w: number}[]>, src: string) {
  const dist = new Map<string, number>([[src, 0]]);
  const visited = new Set<string>();
  // очередь без кучи — граф маленький, честность важнее скорости
  while (true) {
    let u: string | null = null; let best = Infinity;
    for (const [k, d] of dist) if (!visited.has(k) && d < best) { best = d; u = k; }
    if (u === null) break;
    visited.add(u);
    for (const e of adj.get(u) ?? []) {
      const nd = best + e.w;
      if (nd < (dist.get(e.to) ?? Infinity)) dist.set(e.to, nd);
    }
  }
  return dist;
}
```

`adj` строится из `edges.filter(e => !e.closed)`. Длина ребра — евклид по сетке или `turf.length` после проекции, фиксируем один способ в «Как считаем».

### 9.2. Метрики M1 / M2

- `M1` — средняя длина пути до остановки, взвешенная по жителям:
  `M1 = Σ_h residents_h * dist(h, nearest_ostanovka) / Σ_h residents_h`.
- `M2` — доля жителей с парком в N м:
  `M2 = Σ_{h: dist(h, nearest_park) ≤ N} residents_h / Σ residents_h`, `N=400` (ползунок 200–800).
- Дополнительно для 3D: `M3` — % жителей в ветровом застое, `M4` — % зелени в тени 18:00.

Любое действие (перенос остановки = смена `nodeId`, ±переход = ±ребро, коробка = разрыв ребер) → перестроение `adj` → заново все `dist` → новые M1/M2. Цифры не хардкодим — это и проверяет п.9.

### 9.3. Тень — эвристика + 3D

Солнце — `suncalc(date, 55.0960, 36.6100)` → `altitude (высота), azimuth (азимут)`. Длина тени:

```
L = H / tan(alt),  dx = L * cos(az),  dy = L * sin(az)
```

- **2D (ol):** полигон тени = `footprint` сдвинутый на `(dx, dy)` + выпуклая оболочка между оригиналом и сдвигом. Пересечение (`turf.intersect`) с соседними footprint → `% затенения`. Слайдер времени 08:00–20:00.
- **3D (three):** тот же `az/alt` ставит `DirectionalLight.position`, `renderer.shadowMap.enabled=true (PCFSoft)`, здания `castShadow+receiveShadow`, земля `receiveShadow`. Пользователь буквально видит как тень падает на соседние здания — требование закрыто.
- Ночью/низком солнце (`alt ≤ 0`) — тени нет, пишем «солнце за горизонтом».

### 9.4. Ветер — эвристика (не CFD, честно пишем)

Поле 8×8 стрелок. Вход: направление `θ`, скорость `v0`. Для каждого здания-бокса (`w × d × H`):

- наветренная зона: `v = v0 * 1.1` (поджатие);
- боковые коридоры: `v = v0 * 1.2` (ускорение в щелях);
- затишье: конус за зданием длиной `L = 2*H`, внутри `v = v0 * (1 − k)`, `k=0.6` для сплошной коробки, `k=0.3` если рядом зелень (пористый барьер −30%).

Зелень: полигон `Green` снижает скорость на `porosity * 30%` в своем буфере 15 м.

Комфорт двора: нормируем `v` в жилых узлах → `0..1`, среднее. Пороги для заключения: `<0.4` застой, `>0.8` продувает.

Подпись в UI: «упрощенная эвристика для сравнения вариантов, не OpenFOAM». Этого достаточно для хакатона и честно перед жюри.

### 9.5. Коробка мешает потоку — как именно

1. **Пешеходный:** footprint проецируем на ближайшие ребра в радиусе 20 м → эти ребра рвутся (или `length += обход = периметр/2`). Dijkstra пересчитывается → M1 растет. На карте — красные обходы.
2. **Ветровой:** см. §9.4 — за коробкой конус затишья.
3. **Солнечный:** см. §9.3 — тень на соседях.

Три эффекта от одного действия — сильный демо-момент.

### 9.6. Загрязнения и грунтовые воды

```ts
// frontend/lib/city/pollution.ts
export interface PollutionProvider {
  kind: 'mock' | 'openaq' | 'sensor_community' | 'sentinel5p';
  getGrid(bbox: [number,number,number,number]): Promise<number[][]>; // 0..1
}
```

- **P0-демо:** `mock` — IDW-интерполяция из 3 точек-источников (трасса, котельная, парк-фон). Работает офлайн.
- **Адаптеры-заглушки:** `OpenAQ` (PM2.5/NO2 ближайшие станции), `sensor.community`, `Sentinel-5P` (NO2 колонка) — интерфейсы готовы, ключи/прокси — после хакатона. В UI бейдж источника.
- **Визуализация:** `ol/layer/Heatmap` поверх вектора, легенда 0..1.
- **Воды:** синтетика `W = 0.5*близость_к_Протве + 0.3*низина + 0.2*грунт` → 3 класса. Слой-полигоны `ol`, подпись «условно, не изыскания».

### 9.7. Заключение — эвристика ~15 правил

Без LLM (офлайн). Пример правил (`conclusion.ts`):

1. `ΔM1 > +20%` → «Доступность остановок упала: средний путь вырос на X м. Верните остановку или добавьте переход».
2. `M2 < 50%` → «Меньше половины жителей в 400 м от парка — добавьте зелень у домов …».
3. `затенение соседа > 50% в 18:00` → «Коробка H=… затеняет дом … — снизьте высоту / сдвиньте на N м».
4. `комфорт < 0.4` → «Во дворе застой — откройте проезд по ветру / проредите застройку».
5. `комфорт > 0.8` → «Двор продувается — добавьте пористую зелень с запада».
6. `цена > бюджета` → «Вариант превышает бюджет на X — уберите переход …».
7. … + сводка «лучший по M1 / по M2 / по цене» при сравнении проектов.

Текст собирается в `ConclusionBox` + дублируется в API `POST /api/conclusion` для хранения.

## 16. Q&A — вопросы и ответы (душная часть)

**Q1. Кому это нужно и что каждому показывать?**
A: Жюри — пересчет и воспроизводимость (§7 UC-1). Горожанам — пилюли до/после. Архитекторам — 3D/тени/ветер. Городу — проекты + заключение + цена. Матрица — §2.

**Q2. Что считается «настоящим пересчетом», а что — декорацией?**
A: Любое действие меняет `V/E` графа → заново Dijkstra от каждого дома → новые M1/M2. Декорация — когда цифры захардкожены или меняются «на глаз». У нас запрещены захардкоженные цифры, `hash` графа виден.

**Q3. Что такое узел/ребро/дом/притяжение в коде?**
A: См. §4 `DistrictModel`. Узел — метры сетки, ребро — длина + тип, дом — nodeId + жители, притяжение — nodeId + kind.

**Q4. Почему OpenLayers, если кейс разрешает Leaflet/SVG?**
A: Требование заказчика + `Vector + Heatmap + проекции` из коробки + строгие типы. Цена — вес и только client-рендер (`ssr:false`). Геоточность не нужна, маппим сетку в EPSG:3857.

**Q5. А 3D на чем, OpenLayers же 2D?**
A: Да, поэтому два вида одной модели: `ol` — расчетный, `three` — презентационный. Не Cesium: ему нужен глобус/токен/сеть, нам — условный квартал.

**Q6. Как видна тень на других зданиях?**
A: `DirectionalLight` по `az/alt` + `castShadow/receiveShadow` + земля-приемник. Плюс 2D-полигоны тени и панель «сосед затенен N%». Слайдер времени двигает и то, и другое (§9.3).

**Q7. Как считать ветер за 2 дня без CFD?**
A: Никак честный. Эвристика: поле 8×8, конус `L=2*H`, зелень −30% (§9.4). Честно подписываем «не OpenFOAM», для сравнения вариантов хватает.

**Q8. Как считать тени?**
A: `suncalc` → `L=H/tan(alt)` → сдвиг footprint → пересечение с соседями (§9.3). В 3D тот же вектор ставит свет.

**Q9. Как коробка «мешает потоку»?**
A: Три эффекта (§9.5): рвет/удлиняет ребра (M1 растет), дает ветровое затишье, дает тень. Один клик — три пересчета.

**Q10. Откуда спутник/загрязнения/воды?**
A: За 2 дня живой ключ не заведем. `PollutionProvider`: мок IDW + заглушки OpenAQ/sensor.community/Sentinel-5P. Воды — синтетика от Протвы. Везде бейдж «условно» (§9.6).

**Q11. Что за эвристика-заключение?**
A: ~15 `if-then` на русском (§9.7), без LLM чтобы работало офлайн. Собирает текст из ΔM1/M2/тени/ветра/цены.

**Q12. Фронт или бэк считает?**
A: P0 — фронт (мгновенно, прозрачно). Бэк — хранит сценарии и дублирует `/metrics /wind /shadow /conclusion`, чтобы жюри видело серверный расчет.

**Q13. Нужен ли PostGIS?**
A: Нет. JSONB хватает, `turf` на фронте закрывает гео. PostGIS — лишний образ и миграции за 2 дня.

**Q14. Какая геопривязка, если точность не обязательна?**
A: Сетка 0..1000 м + центр Обнинска для солнца/розы. Подложка OSM приглушенная (§4).

**Q15. Как доказать воспроизводимость?**
A: Seed + hash графа в UI, кнопка «Сбросить», e2e «создал — удали». Возврат параметров = те же цифры (§6 NFR-08).

**Q16. Как вписаться в AGENTS.md / Liquid Glass?**
A: Стекло только в панелях, канвас карты сплошной; пилюли/темное стекло/интерактив как в §12; бренд только `<PulseLogo>`; `dark:` везде.

**Q17. Какие технологии итогом и зачем?**
A: `ol@10 + three@0.16x + turf@7 + suncalc + свой dijkstra + JSONB` (таблица §11). Все легкое, офлайн, объяснимое за 20 сек.

**Q18. Как понять что MVP готов?**
A: Чеклист §15, первые 5 пунктов — must. Если их нет — не сдаем.

**Q19. Что режем первым при отставании?**
A: Воды → спутник → ветер → тени → 3D. P0 не трогаем (§13).

**Q20. Что показываем за 90 секунд?**
A: Скрипт §17: закрыть переход → +25% → вернуть → сошлось → поставить коробку → тень на соседе → сохранить проект → вывод.
